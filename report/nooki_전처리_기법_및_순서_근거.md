# 🧩 내 환경에 맞는 전처리 기법 · 적용 이유 · 순서 근거 (Raspberry Pi 5 버전)

> **대상 제품:** 비전 기반 실내 분실물 검출 무인이동체 (PRD 2026.10.06)
> **근거 환경:** 현장 조사 결과 HOME-01 — 30평대 아파트 거실, 밝은 회색 유광 타일, 패브릭 소파 밑, 고양이 1마리
> **시스템:** Raspberry Pi 5 (8GB, 액티브 쿨러) · AI HAT+ 13 TOPS(Hailo-8L) · Camera Module 3 Wide(수평 102°, 롤링셔터, 높이 5cm, 15° 하향, 1280×720) · PWM LED · YOLO11n(또는 YOLOv8n) → Hailo HEF INT8 · 목표 10fps
> **소프트웨어:** Raspberry Pi OS(Bookworm 64bit) · Picamera2/libcamera · OpenCV(CPU) · HailoRT · ROS 2
> 파라미터는 모두 **초기값**입니다. 실측 후 조정이 필요합니다.

### Jetson 버전에서 바뀐 점 요약

| 구분 | Jetson Orin Nano 버전 | Raspberry Pi 5 버전 | 영향 |
|---|---|---|---|
| 모델 가속 | GPU + TensorRT INT8 | **Hailo NPU + HEF INT8** (PC에서 Hailo DFC로 컴파일) | 모델 변환 흐름과 INT8 보정 방식 변경 |
| 전처리 연산 | GPU(CUDA) 가속 가능 | **GPU 없음, CPU(Cortex-A76 4코어)만** | 무거운 필터는 불가, 가능한 일은 카메라 ISP로 넘김 |
| 노이즈 제거 | VPI TNR (소프트웨어 단계) | **카메라 ISP(PiSP) 내장 노이즈 제거** | 소프트웨어 단계 1개가 빠지고 촬영 설정으로 이동 |
| 카메라 제어 | Argus/V4L2 | **Picamera2 컨트롤** (노출·게인·AWB·깜빡임·초점·샤프닝) | 샤프닝 끄기, 초점 고정이 새 필수 항목 |
| 카메라 | 120° 범용 광각 | **Camera Module 3 Wide (102°)** | 물체 픽셀 크기가 약 1.4배 커짐 |
| CPU 여유 | 넉넉함 | **SLAM·Nav2·STT와 CPU를 나눠 씀** | 전처리 전용 프로세스·코어 고정, 탐색 중 STT 정지 |
| 발열 | 여유 | **85°C 근처에서 스로틀링** | 액티브 쿨러 필수, 연속 구동 실측 필요 |

## 2. 적용할 전처리 기법과 적용 이유

### 2-1. 로봇 온보드 (실시간 추론)

|---|---|---|---|---|
| ① | **촬영·ISP 설정** (노출 고정·깜빡임 대응·노이즈 제거·샤프닝 끄기·초점 고정·LED 설정) | 소파 밑에서 LED를 켜면 20cm 이내가 하얗게 날아가고(6-3), 천장 LED에 줄무늬가 생깁니다(1-7). 날아간 픽셀은 복원할 수 없어 촬영 단계에서 막아야 합니다. 소파 밑 2 lux(1-4)의 노이즈는 CPU 대신 **카메라 ISP의 노이즈 제거 블록**으로 처리하고, ISP 기본 샤프닝은 줄눈·털을 강조하므로(2-3, 2-5) 끕니다. Camera Module 3는 오토포커스라 주행 중 초점이 흔들리지 않게 고정합니다 | LED 모드: `AeEnable=False`, `ExposureTime=4000`µs, `AnalogueGain≤4`, `AwbEnable=False`(ColourGains 고정) / 개방 공간: AE + `AeFlickerPeriod=8333`µs(60Hz 전원) / 공통: `Sharpness=0`, `NoiseReductionMode` HighQuality vs Minimal 비교, `AfMode=Manual`·`LensPosition≈3.0`(약 33cm), HDR 끔 / LED PWM 20kHz 이상(RP1 하드웨어 PWM), 확산판 | 카메라 ISP (CPU 0ms) |
| ② | **LED 점등 판단** (노출 × 게인 기반) | 조도가 180 lux에서 2 lux까지 크게 달라집니다(1-3, 1-4). 자동 노출이 평균 밝기를 맞춰버리기 때문에 픽셀 평균으로는 어두운지 판단할 수 없습니다. Picamera2 메타데이터의 `ExposureTime`·`AnalogueGain`을 씁니다 | 노출(ms) × 게인 > 100 이 5프레임 지속 시 ON / 2초마다 1프레임 LED를 끄고, 고정 노출 상태의 평균 밝기 ≥ 70이면 OFF | CPU (0.5ms 미만) |
| ③ | **품질 게이트** (블러·과노출 프레임 제거) | 주행 중 약한 블러가 있고 저조도·롤링셔터에서 심해집니다(6-4). 10px 반지는 2px만 번져도 형태를 잃으므로 흐린 프레임은 버리는 편이 낫습니다 | Laplacian 분산 < 최근 30프레임 중앙값 × 0.6 이면 폐기 / 과노출 픽셀 5% 초과 시 LED 밝기 하향 | CPU (약 1～2ms) |
| ④ | **ROI 크롭** (지평선 위 제거) | 카메라가 5cm 높이에서 15° 아래를 보므로 화면 위쪽은 소파 밑면과 벽입니다(3-1). 물품이 있을 수 없는 영역이라 잘라내면 CPU 연산이 33% 줄어듭니다 | 위쪽 240행 제거 → 1280×480 | CPU (복사 없음) |

| ⑥ | **CLAHE** (LAB L 채널) | 흰 에어팟·은반지가 밝은 회색 타일 위에 있어 대비가 낮고(4-4), 블라인드·소파 그림자로 밝기가 구역마다 다릅니다(1-6). 구역별로 대비를 높이는 CLAHE가 적합하며, L 채널에만 걸어 색 단서를 보존합니다 | clipLimit **2.0**, tileGridSize **(8, 3)** | CPU (약 6～10ms, 색 변환 포함) |
| ⑦ | **원본 해상도 타일링** | 1m 거리 반지 10px, 귀걸이 4px입니다(4-3). 960으로 줄이면 물체가 사라지므로 해상도를 유지한 채 화면을 나눠 추론합니다 | 672×480 타일 2장, overlap 64px. Hailo에는 **uint8 RGB 그대로** 입력(정규화는 HEF 안에서 처리) | CPU (약 1ms) → NPU |
| ⑧ | **반사 마스크 + 다중 프레임 확정** (후처리) | 유광 타일에 비친 LED 반사점이 흰 에어팟과 비슷합니다(2-2, 6-3). 반사점은 화면 속 같은 위치에 고정되어 생기므로 마스크로 표시하고, 사료 같은 방해 물체(5-2)는 여러 프레임 검증으로 걸러냅니다 | 마스크 영역 conf +0.2 요구 / 지도 좌표 5cm 안에서 5프레임 중 3프레임 검출 시 확정 | CPU (약 1～2ms) |

**예상 연산 시간 (추정):** CPU 전처리·후처리 약 12～20ms + Hailo-8L 추론(타일 2장) 약 15～25ms = **약 30～45ms** (예산 100ms).
- CPU는 SLAM·Nav2·ROS 2와 함께 쓰므로, 전처리·추론은 **별도 프로세스로 띄우고 CPU 코어를 고정**(예: `taskset -c 2,3`)하는 것을 권장합니다.
- 오프라인 STT(Whisper)는 CPU를 크게 쓰므로 **탐색 중에는 멈추고**, 물품 입력 단계에서만 돌립니다.
- 수치는 추정치이므로 Pi에서 단계별 시간(`time.perf_counter`)과 `hailortcli benchmark`로 실측해야 합니다.

## 3. 전처리 순서와 근거

### 3-1. 온보드 순서

```text
[카메라 ISP] ① 촬영·ISP 설정 (노출·깜빡임·노이즈 제거·샤프닝 끔·초점 고정)
[CPU]        → ② LED 점등 판단 → ③ 품질 게이트 → ④ ROI 크롭
             → ⑤ 플랫필드 보정 → ⑥ CLAHE → ⑦ 타일링
[Hailo NPU]  → YOLO 추론
[CPU]        → ⑧ 반사 마스크 + 다중 프레임 확정
```

| 순서 | 이 자리에 있어야 하는 이유 | 순서를 바꾸면 생기는 문제 |
|---|---|---|
| ①② 촬영·ISP 설정, LED 판단 → 모든 처리 | 정보 손실은 촬영 순간에 결정됩니다 | 과노출(6-3)이나 블러로 잃은 정보는 이후 어떤 필터로도 복원되지 않습니다 |
| ① ISP 노이즈 제거 → ⑤ 플랫필드 | ISP는 센서 원본(RAW)에 가까운 단계에서 노이즈를 지우므로 가장 효과적이고, CPU를 쓰지 않습니다 | 플랫필드 뒤에 노이즈를 지우면 화면 가장자리 노이즈가 최대 2.5배로 커진 뒤에 지워야 하고, CPU 시간도 추가로 듭니다 |
| ① ISP 샤프닝 끄기 → 모든 처리 | 샤프닝은 ISP 안에서 일어나므로 이후 단계에서 되돌릴 수 없습니다 | 줄눈·털이 강조된 영상이 CLAHE로 한 번 더 강조되어 오검출이 늘어납니다 |
| ③ 품질 게이트 → ④ 이후 처리 | 원본 상태에서 선명도를 재야 정확하고, 버릴 프레임에 CPU를 쓰지 않습니다 | CLAHE 이후에 재면 대비가 인위적으로 커져 흐린 프레임이 통과합니다 |
| ④ 크롭 → ⑤～⑦ | 이후 모든 CPU 단계의 처리량을 33% 줄입니다 | 쓸모없는 소파 밑면까지 CLAHE를 하게 되어 CPU 낭비가 생기고, 밑면의 밝기가 CLAHE 통계를 왜곡합니다 |
| ⑤ 플랫필드 → ⑥ CLAHE | 플랫필드는 "조명 × 반사율" 곱셈 모델에 기반한 보정입니다 | 비선형인 CLAHE를 먼저 하면 곱셈 모델이 깨져 보정 맵이 맞지 않습니다 |
| ⑥ CLAHE(전체 프레임) → ⑦ 타일링 | 두 타일에 같은 밝기 기준이 적용됩니다 | 타일별로 CLAHE를 하면 겹치는 영역의 같은 물체가 타일마다 다르게 보여 병합이 어긋납니다 |
| 추론 → ⑧ 후처리 | 반사점·방해 물체는 영상 필터로 지울 수 없고, 검출 결과와 위치 정보를 같이 봐야 구분됩니다 | 반사점을 영상에서 미리 지우면(인페인팅) 그 자리에 있던 실제 물품도 같이 사라집니다 |

### 3-2. 학습 데이터 순서

```text
ⓐ 원본 수집 → ⓑ 개인정보 처리 → ⓒ 중복 제거·분할 → ⓓ 라벨링
→ (원본마다 증강 사본 생성) ⓕ Copy-Paste → ⓔ 물리 열화 증강 → ⓖ 온보드 동일 전처리
→ (학습 중) ⓗ 기하·색 증강
→ ⓘ Hailo 보정 세트 추출 → ⓙ ONNX → HEF 변환
```

| 순서 | 근거 |
|---|---|
| ⓑ 개인정보 처리 → 저장·라벨링 | 개인정보가 담긴 원본이 저장되거나 라벨링 작업자에게 노출되기 전에 처리해야 합니다 |
| ⓒ 분할 → ⓔ～ⓗ 증강 | 증강 전에 나눠야 같은 원본에서 파생된 이미지가 train과 test에 동시에 들어가지 않습니다 |
| ⓕ Copy-Paste → ⓔ 열화 증강 | 붙여넣은 물체도 실제 물체처럼 노이즈·블러·비네팅을 똑같이 받아야 장면과 자연스럽게 섞입니다 |
| **ⓔ 열화 증강 → ⓖ 전처리** | 로봇에서는 노이즈·블러·비네팅이 **먼저** 생기고 전처리가 **나중**에 적용됩니다. 학습도 같은 순서여야 로봇이 실제로 보는 이미지와 분포가 일치합니다 |
| ⓖ 전처리 → ⓗ 기하·색 증강 | 반전·스케일은 전처리 결과에 영향을 주지 않으므로 마지막에 둬도 되고, 타일 크기를 맞춘 뒤 적용해야 박스 좌표가 정확합니다 |
| ⓘ 보정 세트는 ⓖ 이후에서 추출 | INT8 양자화 범위는 실제 추론 입력(전처리 후 타일)을 기준으로 잡아야 합니다 |
| ⓘ → ⓙ 변환 | Hailo DFC는 컴파일 과정에서 보정 세트로 양자화하므로 보정 세트가 먼저 준비되어 있어야 합니다 |

## 4. 내 환경에서 적용하지 않는 기법

| 기법 | 제외 이유 (내 환경 근거) |
|---|---|
| 전체 프레임 축소 (640/960) | 반지 10px → 약 5～7px, 귀걸이 4px → 약 2～3px로 소실 (4-3) |
| 샤프닝·엣지 강화 (**ISP 기본 샤프닝 포함**) | 타일 줄눈(2-3)과 고양이 털(2-5)이 강조되어 오검출 증가. Picamera2 기본값이 샤프닝 켜짐이므로 `Sharpness=0`으로 꺼야 함 |
| Median·강한 Bilateral·NLM 필터 (CPU) | 얇은 고리 모양 반지가 지워지고, GPU가 없는 Pi CPU에서는 NLM 한 번에 수백 ms가 걸림 → 노이즈는 ISP에서 처리 |
| 전역 히스토그램 평활화 | LED 과노출·반사점(6-3)이 전체 밝기 분포를 왜곡 |
| 영상 전체 왜곡 보정 (Undistort) | 보간으로 작은 물체가 흐려지고 CPU 시간도 듦 → 검출 좌표만 `undistortPoints`로 보정 |
| 딥러닝 초해상화 | 없는 디테일을 만들어 오검출 증가, Hailo-8L 연산 예산 초과 |
| 흑백 변환 | 흰 에어팟·갈색 사료·금 귀걸이를 구분하는 색 단서 손실 |
| 배경 차분 | 카메라가 계속 움직여 배경 모델을 만들 수 없음 |
| 상하 반전·큰 회전·강한 색 증강 | 고정된 카메라 원근 구조와 색 단서를 깨뜨림 |
| 카메라 HDR 모드, 연속 오토포커스 | HDR은 프레임마다 톤이 달라져 학습·추론 분포가 어긋나고, 연속 AF는 주행 중 초점이 흔들려 블러 프레임이 늘어남 |

## 5. 파라미터 확정을 위해 추가로 측정할 것

1. 조도별(2 / 25 / 60 / 180 lux) **노출 × 게인 값**(Picamera2 메타데이터) → LED 점등 임계값 확정
2. 어두운 곳에서 LED를 켜고 **무광 회색 시트 촬영** → 플랫필드 보정 맵
3. 유광 타일 위 **LED 반사점 위치 촬영** → 반사 마스크
4. **체커보드 캘리브레이션** → 왜곡 계수, 지평선 행 위치(ROI 크롭 값)
5. 로봇 카메라로 **거리별 물체 픽셀 크기 실측** → 타일 크기, 주행 경로 간격
6. **교차 편광 필터 유무 비교 촬영** → 반사 억제를 하드웨어로 할지 결정
7. **마루·장판 등 다른 바닥 현장 추가** → 현장 1곳만으로는 일반화 검증 불가
8. **ISP 노이즈 제거 모드 비교** (HighQuality / Fast / Minimal) → 4～10px 물체가 가장 덜 뭉개지는 모드 선택
9. **초점 위치(LensPosition) 결정** → 20cm～1.5m 바닥이 가장 선명한 값 찾기
10. **Pi 실측 시간과 발열** → 단계별 CPU 시간, `hailortcli benchmark` 결과, 30분 연속 구동 후 온도·스로틀링
11. **ONNX vs HEF 정확도 비교** → Hailo INT8 변환 후 작은 물체(4～16px) Recall이 얼마나 떨어지는지 확인
